## 3. Overall Impression

This screen is a genuine, well-executed control tower - the palette, type scale, card/table vocabulary, and dual-coded status pills (color plus explicit text/icon) all track DESIGN.md faithfully, and there is not a shred of AI-slop in it. The biggest opportunity is not visual at all: the page currently tells the who-is-pending story three separate times (Fila de hoje, then Risco operacional, then Transportadoras) before a user reaches anything new, and in the exact state the tool is built for - a slow morning where most or all carriers have not reported yet - the flagship Risco operacional ranking degrades into 11 identical, alphabetically-tied rows that provide zero actual prioritization. Fixing that single ranking and redundancy problem would do more for the daily triage job than any amount of visual polish.

## 4. What is Working

- Status is never color-only. Every pill, calendar dot, and heatmap cell pairs its color with an explicit text label, icon, or hidden string (Recebido/Pendente, Critico/Atencao/Saudavel, CheckCircle2/XCircle plus sr-only text on calendar cells). Live contrast checks on the health-pill variants come out around 6.3-6.8:1 against their tinted backgrounds - comfortably above WCAG AA - directly fulfilling PRODUCT.md's rule against depending on color alone.
- A real loading state, not a blank flash. app/loading.tsx is wired to PageLoading, so the force-dynamic Prisma fetch on this route shows a proper skeleton instead of a white screen - matches the product's visibility-of-status priority.
- A deliberately designed empty/degraded state. When hasOperationalHistory is false, the page renders an explanatory "Operacao aguardando primeiros envios" banner and auto-collapses the deep-analytics details block instead of showing confusing blank charts - this is exactly the kind of empty-state orientation DESIGN.md asks for (though, as noted below, the Risk panel does not fully honor that same restraint).

## 5. Priority Issues

P1 - Risk ranking collapses to noise in the exact state it exists for.
What: Live-tested today (origem=todos, 12 active carriers): every real carrier ties at Risco Atencao 35 with identical factor chips (pendente hoje, sem historico no periodo, sem SLA no periodo), tie-broken only alphabetically.
Why it matters: The Risco operacional table is the single most important triage surface on this page. When it cannot differentiate carriers, which is precisely what happens at the start of a slow day, the ops user has no signal for who to call first, undermining the tool's core promise.
Fix: When most or all rows share a score driven purely by no-data-yet, suppress the numeric score in favor of a distinct state (for example a "sem dado suficiente" chip) or add a secondary, visible tiebreaker such as days-since-last-successful-submission.
Suggested command: clarify

P1 - The same who-is-pending fact is rendered three times.
What: Fila de hoje (top 5 pending), Risco operacional (all pending plus more columns), and the base Transportadoras table (status pill again) all restate pending status on one page (app/page.tsx lines 397-433, 504-561, 789-836).
Why it matters: Cognitive-load check number 1 (single focus) and number 3 (grouping) fail here - a user scans the same 12 names three times before finding anything new, adding real friction to a screen used every single day.
Fix: Make Risco operacional the one authoritative table; fold Fila de hoje into a compact summary strip or filter chip on that same table rather than a separate duplicate list.
Suggested command: distill

P1 - No sticky column on any of the four wide scrollable tables.
What: app/globals.css has zero position sticky rules. The UF heatmap alone renders a 2720px-wide table (.table-wrap greater-than table.heatmap-table min-width 2720px, line 701) for 27 Brazilian UF columns.
Why it matters: Scanning right to compare UF performance loses the carrier-name column entirely, defeating the heatmap's stated purpose of separating a route/region problem from a general carrier problem (app/page.tsx line 634). This is a direct hit on Recognition-rather-than-Recall.
Fix: Make the first cell of .table-wrap tables position sticky, left 0, with a solid background; for the heatmap specifically, consider defaulting to a top-problem-UFs view instead of all 27 columns.
Suggested command: layout

P2 - Filter selection state and decorative icons are invisible to assistive tech.
What: segmented-control active link (app/page.tsx lines 336-344) carries no aria-current or aria-pressed, only a background-color change. Live focus-trace also shows the segmented-control links and plain anchors (Ver tabela completa, queue-more link) fall back to the browser default 1px outline instead of the site's custom 3px blue ring used on .btn. Separately, only the CalendarDays icon (line 705) carries aria-hidden true; AlertTriangle, CheckCircle2, Edit, FileBarChart, History, Plus, XCircle, Layers3 do not.
Why it matters: A keyboard/screen-reader user (Sam) cannot determine which origem filter is currently active, gets an inconsistent focus experience on the page's primary navigation control, and may hear redundant or ambiguous graphic announcements next to text that already says the same thing.
Fix: Add aria-current true to the active segmented-control link; extend the focus-visible rule to cover segmented-control links and plain content links; add aria-hidden true to all decorative icons paired with visible text.
Suggested command: harden

P2 - Loading-skeleton animation ignores prefers-reduced-motion.
What: .loading-bar and .loading-line (app/globals.css lines 1454-1460) and the pulse-line keyframes (lines 1736-1744) animate unconditionally; there is no prefers-reduced-motion media query anywhere in globals.css.
Why it matters: PRODUCT.md states explicitly that animations must respect prefers-reduced-motion. This is a direct, checkable violation of the product's own written accessibility rule, and it fires on every single page load of this route (via app/loading.tsx).
Fix: Wrap the animation in a prefers-reduced-motion no-preference media query, or set animation none under a prefers-reduced-motion reduce query.
Suggested command: harden

## 6. Persona Red Flags

- Has to visually reconcile Fila de hoje (5 of 12), Risco operacional (all 12, tied), and Transportadoras (all 12 again), three passes over near-identical data before reaching anything new.
- Loses row context scanning the 27-column UF heatmap on a 1440px screen (table is 2720px wide, no sticky name column), has to scroll back left repeatedly to re-confirm which carrier row is being read.

- Decorative AlertTriangle, CheckCircle2, Edit, History, etc icons (all missing aria-hidden) sit right next to text that already conveys the same meaning, on every single row of every table, repeated, unnecessary noise per row for a screen-reader user.

## 7. Minor Observations

- .muted gray text (#64748b on white) measures roughly 4.76 to 1 contrast, passes AA for normal text but sits close to the floor at the 12-13px sizes it is frequently used at (.metric-label, .trend-row span, .quality-grid span); a slightly darker gray would give more headroom.
- .btn.compact (app/globals.css lines 639-642, min-height 34px) beats the mobile-only .btn min-height 44px rule (lines 1862-1865) on specificity, so every Historico/Diagnostico/Aplicar compact button stays at roughly 34px tall on the 390px viewport, confirmed live, under the 44 by 44 touch-target guideline. (Non-interactive .calendar-dot at 28 by 28 is fine as-is since it is a status indicator, not a tap target.)
- "Ver tabela completa" (the escape hatch from the truncated 5-item Fila de hoje preview to the full pending list) is a thin inline text link measuring roughly 113 by 14px on mobile, the only path to the rest of the pending list, and it is smaller than most other tap targets on the page.
- The carrier select in the filter form lists all transportadoras (including the inactive "Arquivo inativo teste" demo entry) in one flat, undifferentiated list, no grouping or an inactive suffix to distinguish it before selection.
- The 27-column UF heatmap forces a 2720px-wide table that essentially nobody will fully scan in one sitting regardless of the sticky-column fix above; a top-problem-UFs default with an expand-to-all option would likely see far more actual use.

## 8. Questions to Consider

1. Given that Risco operacional already contains everything Fila de hoje shows (plus more columns and more context), is there a real reason to keep both panels, or would one authoritative table with a "X pendentes hoje" filter chip serve the daily decision better?
2. On a day when literally every carrier is pending (today's real data, live-verified), what should the risk score communicate that is not just "everyone is tied at 35"? Should a distinct no-data-yet state override the numeric score entirely rather than assigning a number that implies false precision?
3. Is the 27-column UF heatmap actually read UF-by-UF by the ops team in practice, or would a top-5-worst-UFs view or a UF-picker plus a focused table better serve the stated goal of separating a route problem from a carrier problem?
